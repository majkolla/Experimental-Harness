Review-Harness: how the system works

An apparatus for measuring whether a panel of AI code reviewers actually delivers the reliability a “two of three approvals to merge” gate implies — or only the appearance of it. This walks the whole pipeline, from config to confidence interval.

1 · The question

Why any of this machinery exists

Put three AI reviewers on a defective patch. If each one wrongly approves 40% of the time, and their mistakes are independent, all three approve 0.43 ≈ 6% of the time. That is the arithmetic that makes redundancy feel safe.

But reviewer mistakes are not independent. They may share a model family, a prompt, a repository context, a defect blind spot. When they do, the unanimous-failure rate is much higher than p³ — and the marginal rates look identical either way. Each reviewer still fails 40% of the time. Nothing on a dashboard changes. The redundancy has quietly stopped existing.

So the system is built to estimate three things that a per-reviewer benchmark cannot: how often a panel fails together, how much of that togetherness is more than chance, and whether it changes when you deliberately couple or decouple the reviewers.

2 · The pipeline

Five stages, one artefact

Everything flows one way. The only durable output is an append-only log of individual reviewer calls; every number in the paper is recomputed from it offline. That means an aggregation bug costs a re-run of the analysis, never a re-run of the models.

python main.py    experiment.json --dry-run    # validate, check balance, print cost
python main.py    experiment.json              # run or resume
python analyze.py experiment.json              # tables + JSON
python -m pytest  tests -q                     # 79 tests, no network

3 · The design

What 576 calls are made of

A run is a fully crossed factorial. Two factors are manipulated, and two more exist to give the estimators something to work with.

The two manipulated factors

FactorLevelsWhat it tests
Panel composition AAA BBB CCC ABC Does mixing model families buy independence? ABC is compared against the equal-weight mixture of the three homogeneous panels, so a randomly drawn seat has the same model distribution either way — the contrast varies coupling with capability roughly held fixed.
Context regime shared / diverse Does handing all three reviewers the same context packet couple them? This is the factor a pipeline engineer can actually change, which is why the paper’s recommendation rests on it.

4 · Seat vs channel

The one distinction that everything else depends on

A seat is a position in the panel; it determines which context packet the call gets. A channel is a fixed model identity. These are deliberately different things, and conflating them was the single subtlest defect in the earlier code.

The bug. for seat, ref in enumerate(seats) welds model identity to seat position: in an ABC panel, model A sits in seat 0 forever. Any property of the seat — which packet it gets, where it lands in the prompt — is then permanently confounded with which model is sitting there.

The fix. Channels rotate across seats by replicate: channel = (seat + replicate) mod n. A channel keeps its model while visiting every seat equally often. The analysis then indexes reviewers by channel, because recombining by seat would pair model A’s outcome with model B’s.

A trap worth knowing about. My first B3 check tested “each model appears in seats with uniform counts”. The welded design passes that — each model appears in exactly one seat, and one number is trivially uniform. The check has to require presence in all n seats. There is now a regression test that builds the welded design and asserts it fails.

5 · One call

What happens between a prompt and a log line

A reviewer is a stateless map: (prompt, patch, context) → vote. It has no memory, no tools, no view of its peers, and no writable workspace. Everything interesting is in how the outcome is classified.

The worst bug in the old code was in resume, not in dispatch. done_ids collected every call_id in the log regardless of status, so a single transient 429 retired that call permanently. Its panel then came out incomplete and was dropped from the analysis. Because error rates differ by provider and by response length, that made missingness correlated with the composition factor — the one confound the design cannot absorb. Only status == "ok" now counts as done.

6 · Execution order

Why the obvious speed-up is the wrong one

The natural implementation runs a panel’s three reviewers in a thread pool. It is fast, it reads cleanly, and it silently destroys the experiment.

7 · From log to outcomes

Turning 576 records into trials

Which patches count

The confirmatory population is the top-left cell of the oracle 2×2: patches that are still vulnerable and functionally passing — near misses that a reviewer could plausibly wave through.

Functionally passingFunctionally failing
Still vulnerable the experiment — Y = 1 on approval excluded: too easy, confounded
Secure secure sibling: approval is correct here repair failure (secondary)

Secure siblings are mandatory. Without them a reviewer that rejects everything scores as a perfect security control. indeterminate labels are excluded from confirmatory analysis: forcing a binary label puts label noise into Y, and label noise on the task is shared by all three reviewers — manufacturing exactly the correlated failure under study.

8 · The null

The single most important idea in the system

To say a panel fails together “more than chance”, you need a number for chance. The tempting one — multiply the individual rates — is wrong in two separate ways. So the baseline is built by design instead: take the same reviewers on the same task, but pair their outcomes across different replicates, so they were never in a panel together.

The two ways the tempting baseline fails

Failure 1 — the plug-in leaks. Estimating the null as p̂ⱼ·p̂ₖ from the same R replicates gives

E[p̂ⱼ p̂ₖ] = (1/R)·q_same + (1 − 1/R)·pⱼpₖ

— a convex combination that puts weight 1/R on the very same-panel joint whose excess you are trying to measure. With p = 0.4, true q = 0.25 and R = 5, the true pairwise penalty is 9.0 pp and the plug-in reports 7.2 pp: understated by exactly one fifth. Recombination puts zero weight on the contaminated term. There is a test for this.

Failure 2 — pooling tasks invents dependence out of nothing. Take two strata of tasks where the reviewers are conditionally independent by construction — easy tasks p = 0.05, hard tasks p = 0.70, zero coupling anywhere. Pool them and compute against pooled marginals:

pooled p0.375pooled q0.24625
Δ = q − p²+10.6 ppC = q ÷ p²1.75
task-conditioned R2/30.3956naive pooled reference0.3164
apparent gate penalty +7.9 pp — every digit of it an artefact of difficulty

This is why recombination is valid only within a task, and why the pooled reference appears in the report as a labelled cautionary row rather than an estimate. Much of the intuitive “LLMs make correlated errors” story is this number.

9 · Why the majority gate lies

The result that decides what you monitor

For three reviewers there is an exact identity — no approximation, no model:

R(2/3) = q₁₂ + q₁₃ + q₂₃ − 2t          and therefore     D(2/3) = 3·dq − 2·dt

The coefficient on the triple is negative. So the sign of the majority-gate effect turns on whether dt/dq exceeds 3/2 — which is not determined by the marginals and the pairwise rates. Two kinds of common cause, both unambiguously coupling, sit on opposite sides of it.

Consequences the report enforces. R_unan and the pairwise gap dq are the primary detectors. R_2/3 is reported because it is what a deployment experiences, not because it is sensitive — and the report prints a shape column (concentrated / diffuse) beside it so its sign is never read without its third-order statistic. A k-of-n gate cannot be monitored safely without a third-order statistic.

There is a two-century-old special case of this. Under total coupling (q = t = p), dt/dq = 1 + p, which crosses 3/2 exactly at p = 1/2 — Condorcet’s condition. A majority gate only improves on a single reviewer when the individual false-approval rate is under one half, and coupling erodes precisely that advantage.

And a harder limit: you cannot skip the triple

Marginals plus all pairwise joints leave the gate risk genuinely undetermined:

LawMasseach peach qR2/3
A¼ each on 111, 100, 010, 0010.50.250.25
B¼ each on 110, 101, 011, 0000.50.250.75

Identical marginals, identical pairwise joints, exact pairwise independence in both — and a threefold difference in how often the gate lets a vulnerable patch through. So “estimate each reviewer’s rate, estimate pairwise correlation, compute gate risk” is not approximate, it is unidentified. That is why full n-tuples are recorded and the 8-cell pattern table is a headline figure, and why the report carries sharp Fréchet bounds on the triple.

10 · Aggregation and uncertainty

Two stages, then resample clusters

The three confirmatory hypotheses

ContrastClaim
H1R_obs shared − diverse Sharing one context packet raises 2-of-3 false approval. The practitioner-facing effect.
H2R_obs ABC − mixture A family-diverse panel does better than the equal-weight homogeneous mixture.
H3D shared − diverse The dependence component rises, not just the level. This is the distinctive claim.

H1 and H3 are separate on purpose. H1 alone cannot distinguish “the intervention decorrelated the panel” from “the intervention made each reviewer individually better” — swapping three weak models (p = 0.45) for three strong diverse ones (p = 0.20) moves R2/3 from 0.425 to 0.104 under exact independence throughout, a 32 pp improvement with zero change in dependence. Marginal capability and dependence are reported as separate columns. Holm corrects across exactly these three; everything CWE- or model-specific is labelled exploratory.

11 · Reading the output

An annotated line from the report

panel/regime     tasks   p_bar   R_obs   R_rec       D    R_un    D_un      dq      dt        shape
ABC/shared           2   0.417   0.250   0.358  -0.108   0.167  +0.121  +0.044  +0.121 concentrated
                     ①      ②       ③       ④       ⑤       ⑥       ⑦       ⑧       ⑨            ⑩
  • 1tasks — how many independent tasks this row averages. Two is a pilot, not a result.
  • 2p_bar — mean individual false-approval rate. Near 0 or 1 the gate saturates and no dependence effect of any size is detectable; the report warns outside [0.05, 0.95].
  • 3R_obs — observed 2-of-3 gate failure. What a deployment actually experiences.
  • 4R_rec — the recombination null: the same reviewers on the same task, never in a panel together.
  • 5D = R_obs − R_rec — the gate dependence penalty. Negative here, which looks like good news and is not.
  • 6R_un — unanimous false approval. The rate that the “p³” intuition gets most wrong.
  • 7D_un — the same penalty on the unanimity gate. +0.121 while D is −0.108: the panel is much worse, and the majority gate is reporting an improvement.
  • 8dq — mean pairwise excess. Positive, so coupling is unambiguously present.
  • 9dt — triple excess. The third-order statistic.
  • 10shape — dt/dq > 3/2, so concentrated: one shared state is fooling the whole panel at once. This is the column that stops ⑤ from being misread.

Above the table sits a per-model missingness tally — non-uniform loss across model families is a confound on the composition factor, not noise. Below it sit the bootstrap contrasts, the naive pooled reference (labelled cautionary), and the secure-sibling approval rates, where approval is the correct behaviour.

12 · Where the guardrails live

79 tests, and what each group is for

An estimator bug here is silent and fatal: the pipeline runs, the tables format, and the conclusions are wrong. So every claim the analysis makes is checked against a process whose dependence structure is known by construction — using exact multisets rather than sampling, so tolerances are ~1e-3 rather than guessed.

FilePins
test_config.pyEvery misconfiguration that would invalidate the design raises: temperature 0, bad divisibility, floating model aliases, missing secure siblings, unequal packet budgets.
test_design.pyB1/B2/B3 hold; the shared arm coincides and the diverse arm does not; channels are model-stable while seats are not; the seat-welded design fails.
test_oracle_isolation.pyNo oracle string appears in any prompt the schedule builds; build_prompt has no parameter one could arrive through; the gate rule is absent from the prompt.
test_schema.pyThe old greedy regex is shown to fail on prose-with-braces and the new parser to succeed; the four failure statuses stay distinct; only two are retryable.
test_runner.pyThe resume bug specifically: a timed-out call is not done. Plus truncated-log survival, retry supersession, and the admission rule.
test_estimators.pyThe gate identity on 200 random laws; closed-form recombination vs O(Rⁿ) brute force; Fréchet bounds valid and attained; the 0.25-vs-0.75 non-identifiability construction; n_eff’s refusals.
test_dgp.pyPlanted independence → D ≈ 0. Planted shared cause → recovered. Heterogeneity alone → the +7.9 pp artefact. Concentrated vs diffuse → opposite signs. Condorcet crossover at p = ½. Plug-in leak = exactly 1/R. End-to-end recovery of a planted contrast, plus a negative control that must look null.
test_pipeline.pyThe whole path against a synthetic provider — no network, no budget. Resume is idempotent; a poisoned log is repaired, not accepted.

13 · What the apparatus cannot yet tell you

  • The task bank is placeholder content. Four structurally correct tasks with illustrative patches. This is the single item that decides whether the paper has a result: it needs near-miss patches — vulnerable and functionally passing — with independently adjudicated labels and an indeterminate class.
  • Two clusters is not an experiment. The demo config’s 576 calls carry two independent clusters. Scale by adding tasks.
  • Model snapshots need verifying against the providers’ current lists before the first paid run.
  • Power is unsimulated, so the smallest detectable effect is unknown. A null result is only publishable if the interval excludes the preregistered effect — “not significant” with a CI spanning [−8, +9] pp supports nothing.
  • Nothing is preregistered yet. Three hypotheses, Holm, and a smallest effect of practical interest should be fixed before the run, not after.
  • The agentic arm is a second treatment, not the baseline. A reviewer that can grep the repo and run tests makes its tool trajectory part of its context — a reviewer assigned one packet re-acquires the others, and two reviewers exploring the same snapshot converge on the same evidence. That is a genuine but unmodelled harness-mediated common cause, and it needs a fresh workspace per call, redirected HOME, a pinned CLI version and network off before it means anything.

The three load-bearing choices, if you remember nothing else.

1. The endpoint is a gate probability, not a correlation — zero pairwise correlation is compatible with R2/3 ∈ {0.25, 0.75}.
2. The null is task-conditioned and built by design — pooling fabricates +7.9 pp, and the plug-in leaks 1/R of the truth into the baseline.
3. The treatment is the harness, not the reviewer count — task difficulty and shared context are both common causes, but only the second is something a pipeline engineer can change, so only the second supports a recommendation.
