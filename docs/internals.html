PART 0

Orientation: what this machine is and what it refuses to do

Four actors, two forbidden edges, one durable artefact.

The harness answers one question: does a panel of n AI reviewers deliver the reliability that a k-of-n merge gate implies, or only the appearance of redundancy? Everything in the codebase is downstream of that question, and most of the code is defensive — it exists to stop the apparatus from measuring something other than what the paper will claim.

The whole system produces exactly one durable output: an append-only JSONL log, one line per reviewer attempt. Every number in every table is recomputed from that log offline. This is not a stylistic preference — it means an aggregation bug costs zero model calls to fix, and it means the gate rule can be changed after the money is spent.

The four boundaries

The most useful mental model is not the module list, it is the boundary map. Four actors own disjoint responsibilities, and two edges that a naive implementation would draw are deliberately absent.

The module layering

Nine modules in hp/, strictly layered. Nothing lower in the stack imports anything higher. This is what makes the offline half of the system testable with no network, no API keys and no SDKs installed at all.

The three invariants everything else serves

1. The reviewer never learns the gate rule and never sees a peer's output. Enforced by the prompt template having exactly two slots.

2. The oracle never reaches the prompt. Enforced by build_prompt(template, patch_text, packet_text) having no parameter through which a label could arrive — and by a test that greps every built prompt for the secret strings.

3. The log is append-only and every derived quantity is recomputed. Enforced by hp/dataset.py and everything above it opening the log read-only.

Known limitation — read before quoting any number

The four shipped tasks are structurally correct placeholders. Real manifests, real sibling pairing, six equal-budget packets each, oracle fields present — but the patch and packet content is illustrative. Every manifest carries "content_status": "PLACEHOLDER -- replace with real CVE material". Nothing may be claimed from a run against this bank.

1.2 The manifest, split down the middle

The manifest is one JSON object, but the code treats it as two disjoint surfaces. This split is the entire oracle-isolation mechanism.

1.3 The six packet kinds

Every task carries the same six kinds of evidence, so the marginal distribution of context quality is comparable across tasks as well as across the two regimes. This uniformity is what lets the shared-vs-diverse contrast be about coupling rather than about who got the better material.

Why packets are committed, never generated

A packet builder that runs inside the experiment — especially an LLM one — sits upstream of all n reviewers and becomes an unmeasured common cause. It would inject exactly the correlated failure the study claims to measure. So tools/make_demo_tasks.py runs offline, writes the files, and the files are committed and hashed at load (Task.packet_bank_hash).

1.4 The prompt template

prompts/reviewer.md is 29 lines with exactly two substitution slots. The config loader refuses a template missing either one.

PART 2

The config gauntlet: fifteen ways to be told no

hp/config.py — everything here runs before a single token is spent, and it raises rather than warns.

The failure mode this module guards against is not "the run crashes". It is "the run completes and the numbers mean something other than what the paper claims". That failure is silent, expensive and unrecoverable, so every design-invalidating misconfiguration is a hard ConfigError.

2.1 Three gates worth dwelling on

temperature > 0 — the one that would silently zero every result

At temperature 0 the R replicates are one measurement copied R times. The cross-replicate recombination baseline (§7.3) then has nothing to recombine — every "independent" pairing draws the same outcome — and every dependence estimate collapses to zero by construction. The run would complete, the tables would format, and the paper would report a null result caused by a decode setting.

The three divisibility conditions

ConditionDemo valueWhat breaks without it
R ≥ 36 ≥ 3The recombination null for n = 3 needs triples of distinct replicate indices; below 3 there are none and recomb_stat returns None.
P mod n == 06 mod 3 = 0The diverse arm uses cyclic step P // n. If it doesn't divide, the n seats of a replicate can collide and the "diverse" arm stops being diverse.
R mod P == 06 mod 6 = 0Each packet is used n·R/P times per cell and R/P times per seat. Non-integer means B1/B2 hold only approximately, and the balance assertion — which demands exact uniformity — fails.
R mod n == 06 mod 3 = 0Seat rotation is channel = (seat + rep) mod n; unless n divides R, some model visits some seat more often than another and B3 fails.

2.2 Function reference — hp/config.py

load(cfg_path) → dict

Reads the JSON, applies eleven defaults, runs all fifteen gates, loads every task, and returns the config dict enriched with private keys: _root, _prompt, _prompt_hash, _tasks, _config_hash.

The _config_hash covers only the ten scientifically meaningful fields (name, seed, temperature, replicates, models, panels, regimes, packets_per_task, gate, max_tokens). Changing workers or timeout_s deliberately does not change the hash, because those do not change what is being measured — so a resumed run after an operational tweak still stamps the same experiment identity.

build_prompt(template, patch_text, packet_text) → str

Two string replacements. This is the only function in the codebase that assembles reviewer input.

Its signature is the enforcement mechanism for oracle isolation. There is no parameter through which a label, CWE id or exploit note could arrive, and tests/test_oracle_isolation.py::test_build_prompt_has_no_channel_for_the_oracle asserts the arity stays at three.

class Task

A frozen task. Holds task_id, root, patch_text, a packets list of (packet_id, text, sha12) triples, and the raw manifest as a private attribute.

Two accessors, deliberately separated: prompt_inputs(packet_index) is the reviewer-visible surface; .oracle is the analysis-only surface. Also exposes .cluster — which defaults to task_id but should be the CVE id, because sibling patches of one CVE are not independent bootstrap draws.

_load_task(dir, packets_per_task) → Task

Validates one task directory: manifest and patch exist, label ∈ {vulnerable, secure, indeterminate}, functional ∈ {pass, fail, unknown}, packet count exact, packet lengths within 2× of each other. Hashes each packet.

_sha12(s) → str

First 12 hex chars of SHA-256. Used for the config hash, the prompt hash and each packet hash — short enough to eyeball in a log line, long enough that collisions are not a concern at this scale.

The design: what 576 calls are made of

hp/design.py — a pure function of the config. No I/O, no network, fully auditable before spending.

3.1 The factorisation

The schedule is a five-fold nested product. Nothing is sampled; every cell of the design is visited a fixed number of times.

3.2 The cyclic packet map — the causal contrast

This is the single most important function in the design module. It decides which context packet each seat receives, and it is what makes shared-vs-diverse a manipulation of coupling rather than of context quality.

3.5 B4: shuffling, and why the obvious speed-up is wrong

The temporal-collocation trap

The obvious way to parallelise is one thread pool per panel: launch a panel's n reviewers together, collect three votes, move on. That is precisely wrong. It puts the panel's n calls at the vendor in the same instant, sharing cache state, load, and any service-side condition. Panel-level coupling then appears by construction and is indistinguishable from the coupling under study.

A panel is a grouping in the design, not an event in time. §5.2 shows the admission rule that replaces it.

3.6 Function reference — hp/design.py

packet_index(regime, replicate, seat, n_packets, n_seats) → int

The cyclic map above. Pure arithmetic; the single point where the shared/diverse manipulation is expressed.

build_schedule(cfg) → list[dict]

Five nested loops over tasks × panels × regimes × replicates × seats, emitting one call descriptor each. Then asserts balance, then shuffles, then stamps dispatch indices.

Note the ordering: assert before shuffle. Balance is a property of the multiset of calls, so it is checked while the structure is still legible, and the shuffle cannot break it.

assert_balanced(calls, cfg) → True | raises BalanceError

Groups calls into (task, panel, regime) cells and checks, per cell: cell size = R·n; B1 every packet used exactly n·R/P times; B2 every (seat, packet) and every (channel, packet) pair appears exactly R/P times; B3 every model in every seat with equal non-zero counts; plus regime semantics (shared ⇒ 1 distinct packet per replicate, diverse ⇒ n). Finally checks B1's second half: the per-packet count is equal across regimes.

Raises, never warns. A warning in a batch job is a line of output nobody reads; by the time the numbers look strange the money is gone.

cost_table(cfg, calls) → dict

Preflight summary: total calls, and counts broken down by model and by provider — so a per-provider cost estimate is possible before dispatch. Crucially also reports independent_clusters.

4.2 The verdict contract

validate() is hand-written rather than delegated to jsonschema, and that is deliberate: the contract is four fields, and an experiment should not silently change shape because a validation library was upgraded mid-run. It also catches things a loose schema would not — isinstance(conf, bool) is rejected explicitly, because in Python True is an instance of int and would otherwise sail through as a confidence of 1.0.

Why there are two schemas

OpenAI's strict: true mode rejects validation keywords like minimum and maximum. So _STRICT_SCHEMA is the structural subset sent on the wire, and schema.validate still enforces 0 ≤ confidence ≤ 1 on the way back in. Neither layer is redundant: the wire schema makes malformed output rare, the local validator makes it impossible for a malformed verdict to reach the analysis.

Two config knobs that exist for real provider quirks

  • send_temperature: false per model — reasoning models reject a temperature parameter outright. Setting this omits it and records that the decode setting is the provider default. Note the tension with the temperature > 0 gate: the gate guarantees the configured temperature is non-zero, but a model that ignores it is relying on the provider's own sampling being stochastic.
  • max_retries=0 on every SDK client — attempts are counted and logged by the harness, not by the SDK. An SDK that silently retries three times inside one call would make the missingness structure invisible.

4.4 Exception → status classification

_classify matches on the exception's class name and any status_code attribute, never on imported SDK exception types. That is what keeps hp/providers.py importable — and the whole test suite runnable — with no provider SDK installed at all.

4.6 Function reference — hp/schema.py and hp/providers.py

schema.validate(obj) → dict | raises SchemaError

Hand-written validation of the four-field contract. Returns a normalised dict with confidence coerced to float.

schema._json_candidates(text) → generator[str]

Yields every balanced-brace substring, outermost first, string- and escape-aware.

schema.parse_verdict(payload) → (verdict, None) | (None, reason)

Accepts either a dict (provider-native structured output — the normal path) or raw text (the fallback). Never raises, never guesses: a response either yields a validating verdict or yields a string explaining why it did not.

providers.call_once(spec, prompt, cfg) → record

One attempt. Dispatches to PROVIDERS[spec["provider"]], catches everything, classifies, parses, and returns a record.

Never raises for a provider fault. A failed call is data, not a crash — the except Exception is deliberate and annotated as such in the source.

providers._record(status, verdict, raw, meta, started) → dict

Assembles the response half of a log line: status, verdict, flattened decision and confidence, the raw text, timestamps, latency, and whatever provider metadata was captured (served_model, stop_reason, token counts).

providers.call_with_retries(spec, prompt, cfg, rng) → list[record]

Loops up to max_attempts, breaking on ok or on any non-retryable status. Backoff is min(30, 2**attempt * (0.5 + rng.random())).

Returns every attempt, not just the last, each stamped with an attempt index — so the log carries the full missingness structure. attempt is an operational counter and must never be treated as a replicate index in analysis.

Yields records, skipping blank lines and warning-but-continuing on a line that is not valid JSON.

6.2 Function reference — hp/dataset.py

load_records(log_path, read_log) → (latest, attempts, status_by_model)

One pass over the log. latest maps call_id → the last ok record; attempts counts lines per call id; status_by_model tallies (model_ref, status) pairs for the missingness table.

read_log is injected rather than imported, which is why dataset sits below runner in the layering and can be tested against a list literal.

build_cells(cfg, records, abstain_as_approval=False) → dict[(task,panel,regime), cell]

Groups by (task, panel, regime, replicate), keeps complete replicates as channel-indexed tuples, counts incomplete ones and records which replicate indices they were. Each cell carries cluster, label, functional and a homogeneous flag (computed as len(set(panel_seats)) == 1, which gates n_eff).

primary(cells) / secure_controls(cells) → dict

The two populations of the 2×2 above. primary is label == "vulnerable" and functional == "pass"; secure_controls is label == "secure".

missingness_table(status_by_model) → list[row]

Per-model status counts plus a loss_rate. Published beside every result.

Non-uniformity in this table is a confound, not noise. If model B loses 4% of its calls and model A loses 0.5%, the BBB panels are estimated from a different — and systematically easier or harder — subset than the AAA panels, and the composition contrast is contaminated.

The code computes R_obs by direct counting and then stores identity_residual = |gate_risk(trials,2) − (Σq − 2t)| as a self-check on the log rather than as a reported quantity. 7.3 The null: within-task cross-replicate recombination

This is the single most important idea in the system. Everything the paper claims about dependence is a comparison against this baseline, so a wrong null is a wrong paper.

7.5 The two tempting nulls, and how each one lies

Wrong null #1 — plug in p̂j p̂k

The obvious independence baseline: estimate each reviewer's rate, multiply. It has a closed-form bias:

The plug-in "independence" reference is a convex combination that puts weight 1/R on the very same-panel joint whose excess is being measured. It therefore leaks a 1/R fraction of the true dependence into the null, and always in the same direction: it hides dependence.

Measured, not argued

test_plugin_null_leaks_one_over_R_of_the_dependence constructs a shared-cause process with p = 0.4, qsame = 0.25 and R = 5 across 20,000 cells. True pairwise penalty: 9.0 pp. Recombination estimate: 9.0 pp. Plug-in estimate: 7.2 pp — understated by exactly one fifth. The test also asserts the sign of the error is always the same.

It is still computed and reported, as R_plugin, labelled a robustness display only.

8.1 The three confirmatory hypotheses

NameEstimandDirectionWhat it would establish
H1_regime_R_obsRobs(shared) − Robs(diverse), averaged over panel templatesgreaterShared context raises the false-approval rate a deployment actually experiences.
H2_composition_R_obsRobs(ABC) − mean{Robs(AAA), Robs(BBB), Robs(CCC)}lessA heterogeneous panel is safer than a homogeneous one of matched capability.
H3_regime_DD(shared) − D(diverse)greaterThe dependence penalty itself — not just the rate — is caused by shared context.

Why H2 is stated against a mixture, not against a single panel

Comparing ABC to (say) AAA alone confounds coupling with capability: if A is simply a better reviewer, ABC looks worse for reasons that have nothing to do with diversity. Stating it against (R_AAA + R_BBB + R_CCC)/3 means a randomly drawn seat has the same marginal model distribution in ABC and in the mixture, so the contrast comes much closer to holding capability fixed while varying only coupling.

What the contrast still does not buy

It does not make model families exchangeable. Model identity bundles capability, training data and tuning inseparably. So the claim H2 can support stays operational: these panel templates, on this task bank — not "diversity per se". That restriction is written into the docstring of contrast_composition, and it should be written into the paper the same way.

Why the regime contrast is unusually clean

The same task population is evaluated in both arms, and B1 guarantees identical marginal packet exposure. Stable task difficulty therefore cancels from the contrast by construction rather than by adjustment — no covariate, no matching, no model.

8.2 The bootstrap

Intervals are percentile: vals[int(α/2·(N−1))] to vals[int((1−α/2)·(N−1))]. One-sided p-values use the add-one correction (1 + #{v ≤ 0}) / (N + 1), which keeps p strictly positive — a bootstrap p of exactly zero is a statement about the number of draws, not about the evidence.

8.3 Holm, over exactly three tests

Applied across CONFIRMATORY only. Everything CWE-specific or model-specific lives in EXPLORATORY and is reported uncorrected and labelled as such — because correcting across an open-ended family would be either dishonest (if the family is quietly truncated) or useless (if it is not). test_holm_corrects_across_exactly_three_confirmatory_tests asserts both the arithmetic (0.01 → 0.03, 0.04 → 0.08, 0.20 → 0.20) and that the confirmatory set is exactly those three names, so silently adding a fourth breaks the build.

The pairing that matters most

The positive control (a planted regime effect recovered with intervals excluding zero) and the negative control (an identical pipeline on data with nothing planted, which must look null) are the two halves of the same guarantee. A pipeline that only ever finds effects is not evidence of anything.

11.2 What is not done

  1. The real task bank. The single item that decides whether the paper has a result. It needs near-miss patches — vulnerable and functionally passing — with independently adjudicated labels and an indeterminate class. Everything else in this document is scaffolding around this gap.
  2. Two clusters is not an experiment. The demo config's 576 calls carry two independent clusters. Scale by adding tasks — adding replicates buys precision within a task and almost nothing across tasks.
  3. Model snapshots need verifying against the providers' current lists before the first paid run. The pinning regex checks shape, not existence.
  4. Power is unsimulated. A closed-form Bernoulli calculation would assume independent calls and claim adequate power at a fraction of the true requirement. The procedure is to resample complete pilot tasks and simulate the exact blocked design at 30/60/100 tasks × 6/12/24 replicates through the planned estimator, bootstrap and correction end to end.
  5. Nothing is preregistered. Three hypotheses, Holm, and a smallest effect of practical interest (e.g. 5 pp on R2/3) should be fixed before the run. A null result is only publishable if the interval excludes that effect — "not significant" with a CI spanning [−8, +9] pp supports nothing.
  6. The agentic arm is a second treatment, not the baseline. A reviewer that can grep the repo and run tests makes its tool trajectory part of its context: a reviewer assigned one packet re-acquires the others, and two reviewers exploring the same snapshot converge on the same evidence. That is a genuine but unmodelled harness-mediated common cause, and it needs a fresh workspace per call, redirected HOME, a pinned CLI version and network off before it means anything.
  7. General-n LP bound on gate risk from moment constraints — only if the paper generalises past n = 3. The Fréchet triple bounds are exact for n = 3 and do not extend.
If you remember only three things

1. The endpoint is a gate probability, not a correlation. Zero pairwise correlation is compatible with R2/3 ∈ {0.25, 0.75}.

2. The null is task-conditioned and built by design. Pooling fabricates +7.9 pp from pure heterogeneity; the plug-in leaks 1/R of the truth into the baseline.

3. The treatment is the harness, not the reviewer count. Task difficulty and shared context are both common causes, but only the second is something a pipeline engineer can change — so only the second supports a recommendation.
